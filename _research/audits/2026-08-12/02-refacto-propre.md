# Audit — Refacto propre : inventaire des duplications et du couplage (DATE-MANQUANTE)

## Verdict

Le decoupage d'Ocean est **bien pense et respecte a ~90 %** (`lib/data` lecture / `lib/actions` ecriture / `lib/domain` regles, facade d'exports explicite, commentaires qui portent les invariants), mais il **fuit exactement aux trois frontieres qui comptent**. (1) L'invariant « un contenu programme est un contenu en file » n'appartient a aucune couche : il est reparti entre trois Server Actions, une RPC qui ne sait qu'**ajouter**, zero trigger DB et quatre UI qui le recomposent chacune a leur facon — d'ou les deux seuls defauts bloquants du perimetre (deprogrammer depuis le calendrier laisse le job vivant → publication non voulue chez un vrai client ; re-dater depuis le composer ne realigne pas `run_at` → publication a l'ancienne heure). (2) La frontiere `apps/web` ↔ `apps/worker` **n'a pas de lieu** : `packages/shared` est declare, quasi vide et importe par personne (0 importeur ; `apps/worker/package.json` ne declare que `pg`), donc Brevo, la config OAuth, les specs medias, les quotas et le vocabulaire du domaine vivent en 2 a 7 exemplaires, plusieurs derriere `import "server-only"` que le worker ne peut structurellement pas consommer — le worker publie sans valider, sans quota et sans prevenir personne. (3) La frontiere UI ↔ ecriture est **asymetrique** : une douzaine de boutons emettent un `toast.success` sans qu'aucune Server Action ne parte, alors que l'action existe et est deja cablee ailleurs (reprogrammer, dupliquer, reconnecter un compte, corriger un alt, supprimer un visuel). **Risque principal a 5 ans** : le nombre de chemins d'ecriture faillibles croit lineairement avec les features parce que la regle vit dans des commentaires et non dans le code ; le vocabulaire du domaine diverge entre deux apps qui ne partagent aucun type ; et le shell applicatif charge O(taille totale du tenant) a chaque rendu de layout, donc l'app ralentit mecaniquement a mesure qu'elle sert — jusqu'a un mur dur qui tombe sur toutes les pages a la fois.

## Findings (tries par severite P0 -> P3)

### [P0] Deprogrammer depuis le calendrier laisse le `publish_job` vivant : le worker publiera quand meme — go-live : bloquant

- **Ou** : [components/app/calendar/calendar-actions.ts:177](../../../apps/web/components/app/calendar/calendar-actions.ts#L177) (`performUnschedule`) → [:42](../../../apps/web/components/app/calendar/calendar-actions.ts#L42) (`persistBatch`) → [lib/actions/content.ts:293](../../../apps/web/lib/actions/content.ts#L293) ; [supabase/migrations/020_publish_jobs.sql:178](../../../supabase/migrations/020_publish_jobs.sql#L178).
- **Constat** : `performUnschedule` mappe chaque item vers `null` et appelle `scheduleContentItem({ scheduledAt: null })`. Cette action met `scheduled_at = null` **sans changer le statut** (le contenu reste `scheduled`) puis appelle `enqueue_publish_jobs`, qui sort en `return 0` des que `v_at is null` — **sans rien annuler**. `cancel_publish_jobs` n'a qu'un seul call site dans tout le depot ([content-status.ts:98](../../../apps/web/lib/actions/content-status.ts#L98)), jamais atteint ici. `isMovable` ([calendar-schedule.ts:20](../../../apps/web/components/app/calendar/calendar-schedule.ts#L20)) autorise explicitement le statut `scheduled` : les contenus a jobs vivants sont bien concernes. Aucun filet DB (le trigger de statut est `BEFORE UPDATE OF status`), et le claim worker ne filtre que sur `publish_jobs.status` + `run_at <= now()`.
- **Scenario d'echec / cout a l'echelle** : le client demande d'annuler la publication de demain. Etienne coche le post au calendrier, clique « Annuler la planification » : toast de succes, le post quitte la case. La ligne `publish_jobs` garde `run_at = demain 10 h`. Demain a 10 h, le worker claim le job et **publie sur le compte Instagram du client**. Attenuation purement temporelle : les publishers sont encore des stubs et l'app Coolify worker n'existe pas — le jour ou elle existe, le defaut est actif.
- **Pourquoi ca bloque le scaling** : tant que « la date du contenu » et « le `run_at` du job » sont realignes par une RPC qui ne sait qu'**ajouter**, chaque nouveau chemin de deplanification (portail, lot, PWA, annulation client, Lot 5) rouvrira la meme fenetre. La file doit etre **derivee** de l'etat du contenu, pas maintenue a la main par chaque ecran.
- **Reco** : immediat — `scheduleContentItem` appelle `cancel_publish_jobs` quand `scheduledAt === null` (une ligne, aucun autre appelant impacte). Durable — un trigger `AFTER UPDATE OF scheduled_at, status ON content_items` qui synchronise la file (enqueue / realign / cancel), pour qu'elle cesse de dependre du call site.
- **Effort** : S (fix) / M (trigger)   **Impact** : fort
- **⚠ Comportement** : oui   **Regle CLAUDE.md** : 15, 16

### [P0] Re-dater un contenu deja programme depuis le composer ne realigne pas `run_at` : il partira a l'ancienne heure — go-live : bloquant

- **Ou** : [lib/actions/content.ts:105](../../../apps/web/lib/actions/content.ts#L105) (`baseFields.scheduled_at`) et [:142](../../../apps/web/lib/actions/content.ts#L142) (update inconditionnel) ; garde d'edition [content/[contentId]/edit/page.tsx:29](../../../apps/web/app/(app)/clients/[clientId]/content/[contentId]/edit/page.tsx#L29) ; contre-exemple correct [content.ts:311](../../../apps/web/lib/actions/content.ts#L311).
- **Constat** : `saveContentItem` ecrit `scheduled_at` **pour tous les statuts** (le champ est dans `baseFields`, applique a l'insert comme a l'update) et n'appelle **jamais** `enqueue_publish_jobs`. Or la page d'edition n'interdit que `publishing|published|partially_published` (`READ_ONLY`) : un contenu **deja `scheduled`**, dont les jobs sont vivants, est editable dans le composer. `publish_jobs.run_at` est recopie de `scheduled_at` **a l'enfilement** ([020:190](../../../supabase/migrations/020_publish_jobs.sql#L190)) et reste donc fige ; aucun trigger ne synchronise. Le composer confirme malgre tout par « Contenu programme » des que `draft.scheduledAt` est non nul ([composer-screen.tsx:184](../../../apps/web/components/app/studio/composer/composer-screen.tsx#L184)).
- **Scenario d'echec / cout a l'echelle** : contenu programme mardi 18 h, jobs enfiles. Etienne rouvre le composer, decale a jeudi 09 h, enregistre. L'UI, le calendrier et la grille affichent jeudi 09 h. Le worker publie **mardi 18 h** chez le vrai client — deux jours avant la date annoncee, sur un contenu peut-etre encore en retouche. Rien ne le signale : pas de watchdog, pas d'ecran de coherence.
- **Pourquoi ca bloque le scaling** : chaque nouveau point d'entree qui touche `scheduled_at` (PWA, duplication programmee, creneaux recurrents, import, actions IA du Lot 5) devra se souvenir d'appeler la RPC. La regle vit dans un commentaire, pas dans le code : le nombre d'oublis croit avec le nombre d'actions, et chacun reste invisible jusqu'a une publication au mauvais moment.
- **Reco** : extraire un helper unique `setScheduledAt(supabase, org, client, contentId, at)` dans [`_helpers.ts`](../../../apps/web/lib/actions/_helpers.ts) qui fait l'`update` **puis** la RPC (idempotente, no-op hors statut `scheduled`), appele depuis `saveContentItem` ET `scheduleContentItem` — aucun autre code n'ecrit la colonne. Durable : le meme trigger qu'au finding precedent (les deux P0 se corrigent ensemble). Cote UI, n'annoncer « Contenu programme » que si une transition a reellement eu lieu.
- **Effort** : S (helper) / M (trigger + UI)   **Impact** : fort
- **⚠ Comportement** : oui   **Regle CLAUDE.md** : 15, 16, 27

- **Ou** : [components/app/studio/board-kanban.tsx:79](../../../apps/web/components/app/studio/board-kanban.tsx#L79) ; [components/app/studio/board-state.ts:267](../../../apps/web/components/app/studio/board-state.ts#L267).

Si la seconde echoue, le code se contente d'un `toast.error` ([:89](../../../apps/web/components/app/studio/board-kanban.tsx#L89)) et d'un `router.refresh()` : le contenu reste `scheduled` en base **avec `scheduled_at` a `null`**, et `applyStatusIntent` a deja appele `enqueue_publish_jobs` alors que la date etait nulle → la RPC a renvoye 0. `scheduleBatchCommit` a la meme sequence et son `rollbackStatus` ([:283](../../../apps/web/components/app/studio/board-state.ts#L283)) ne touche que les overrides client, pas la ligne DB. ### [P3] La regle 18 (max 5 tentatives) est implementee dans l'adaptateur SQL, pas dans le moteur : aucune couverture — go-live : apres

- **Ou** : [apps/worker/src/db/pg-store.ts:166-172](../../../apps/worker/src/db/pg-store.ts#L166) ; [apps/worker/src/engine.ts:128](../../../apps/worker/src/engine.ts#L128) ; double de test [engine.test.ts:67](../../../apps/worker/src/engine.test.ts#L67).

- **Reco** : remonter la decision dans `engine.ts` (le moteur calcule `attempts + 1 >= maxAttempts` et appelle explicitement `store.failPermanent` ou `store.retry(job, delay)`) ; le store redevient un ecrivain sans jugement. Ajouter deux tests (`attempts = 4` → `failPermanent`, `attempts = 3` → `retry`) que le `FakeStore` actuel suffit a couvrir.
- **Effort** : S   **Impact** : moyen
- **⚠ Comportement** : non   **Regle CLAUDE.md** : 18
