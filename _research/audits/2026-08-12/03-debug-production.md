# Audit — Debug production : root cause des fragilités, edge cases, fix robustes (DATE-MANQUANTE)

## Verdict

Ocean est écrit par quelqu'un qui connaît les bons invariants : la règle 15 est commentée à l'endroit exact où elle vit ([engine.ts:6-12](../../../apps/worker/src/engine.ts#L6)), le claim est réellement atomique en `FOR UPDATE SKIP LOCKED`, les tokens sont en Vault et ne touchent jamais le navigateur, les gardes SQL 008/013 refusent bien les statuts d'exécution à `authenticated`. **Le problème n'est pas la conception, c'est que chaque invariant n'est appliqué qu'à UN seul endroit du chemin nominal, et que ce sont les chemins de bord qui se déclenchent en production.** Concrètement, trois classes de défaillance sortent de cet audit et conditionnent l'usage réel immédiat : (a) **l'ancre d'idempotence est contournable par quatre sorties distinctes** — fenêtre de grâce évaluée avant le test `publishStartedAt` (F01), échec terminal évalué avant lui aussi (F18), cascade FK qui efface l'ancre (F15), ré-enfilement d'une cible non-`published` (F16) — chacune convertissant une publication réussie en « échec » affiché, donc en republication manuelle, donc en double post chez un vrai client ; (b) **la file n'est jamais recoupée avec l'état métier** : le claim ne joint pas `content_items`, donc un contenu mis à la corbeille (F03) ou déprogrammé pendant le lease (F21) part quand même ; (c) **le parcours reviewer — cœur commercial du produit — est simultanément cassé et exploitable** : aucune session n'est jamais posée à l'acceptation d'invitation (F08), et la même route ouvre une session sur un compte EXISTANT sans preuve de possession de la boîte mail (F09, prise de contrôle inter-tenant). En face, la capacité de diagnostic est **nulle** : pas de Sentry (ni web ni worker), pas de watchdog pg_cron malgré les commentaires qui s'y réfèrent comme à un filet existant ([pg-store.ts:79-81](../../../apps/worker/src/db/pg-store.ts#L79)), aucune notification, aucun appel Brevo dans le worker, ~52 lectures Supabase qui ne lisent jamais `error` (F14). **Risque à 5 ans** : tous les modes de défaillance identifiés sont *silencieux et non détectables a posteriori* (la trace du job détruit disparaît avec lui) ; leur nombre absolu croît linéairement avec le volume publié sans jamais devenir visible, et le coût de détection reste constant (un humain qui vérifie) pendant que le volume, lui, monte. Ajouté à un worker strictement séquentiel et sans timeout (F23), la plateforme n'a ni débit horizontal ni observabilité : elle tiendra tant qu'Étienne regardera chaque post, et pas un jour de plus.

## Fonctionnement réel observé

### 1. Le chemin d'une publication, de bout en bout

```
UI (studio / grille / calendrier / kanban)
  └─ Server Action  saveContentItem | applyStatusIntent | scheduleContentItem | trashContent
       ├─ UPDATE content_items          → garde SQL 008 (BEFORE UPDATE OF status)
       ├─ delete+insert content_targets / content_media / labels   [erreurs NON lues]
       └─ rpc enqueue_publish_jobs      [retour et erreur NON lus]
            └─ INSERT publish_jobs (1 par content_target API non published/canceled/skipped)
~~~~~~~~~~~~~~~~~~~~~~~~ frontière process (2 apps Coolify) ~~~~~~~~~~~~~~~~~~~~~~~~
apps/worker — boucle while(running), tick toutes les pollIntervalMs
  ├─ reapExpired()                       pg-store.ts:78
  ├─ claim() FOR UPDATE SKIP LOCKED      pg-store.ts:52   (jusqu'à 10 par tick, SÉQUENTIEL)
  └─ processJob()                        engine.ts:27
       [1] fenêtre de grâce  → deadLetter          ← AVANT tout
       [2] prepare()  token Vault → NeedsReauth → failPermanent
       [3] checkQuota() → deferForQuota
       [4] publishStartedAt ? recoverStartedJob : publishFresh   ← la règle 15 est ICI, en 4e
  └─ écriture DOUBLE : publish_jobs (technique) + content_targets (métier) + recomputeParent
```

Faits structurants, à garder en tête pour tout le rapport :

- **L'ordre des gardes dans `processJob` est faux.** La fenêtre de grâce ([engine.ts:34](../../../apps/worker/src/engine.ts#L34)) et la résolution de token ([engine.ts:41-46](../../../apps/worker/src/engine.ts#L41)) s'exécutent **avant** le test d'idempotence ([engine.ts:61](../../../apps/worker/src/engine.ts#L61)). Deux sorties terminales précèdent donc la seule branche qui interroge le conteneur (`getContainerStatus`). C'est la racine commune de F01 et F18.
- **La file est la seule source de vérité à l'exécution.** Le claim ([pg-store.ts:55-71](../../../apps/worker/src/db/pg-store.ts#L55)) ne joint jamais `content_items` : ni `status`, ni `deleted_at`, ni `scheduled_at` ne sont relus avant publication. `grep -rn deleted_at apps/worker/src` = zéro occurrence. Racine de F03 et F21.
- **L'ancre d'idempotence vit sur le JOB, pas sur la CIBLE.** `publish_started_at` et `external_container_id` sont des colonnes de `publish_jobs`. Tout chemin qui crée un nouveau job pour la même `content_target` repart d'une ardoise vierge — et l'index unique partiel ([020:115-117](../../../supabase/migrations/020_publish_jobs.sql#L115)) exclut explicitement les statuts terminaux, donc il ne bloque rien dans ce cas. Racine de F15 et F16.
- **Aucune écriture n'est fencée.** `markPublishStarted`, `succeed`, `retryOrFail`, `extendLease`, `patchProgress`, `deferForQuota` écrivent toutes en `where id = $1` ([pg-store.ts:94-235](../../../apps/worker/src/db/pg-store.ts#L94)) : le `worker_id` posé au claim n'est vérifié nulle part, aucun `rowCount` n'est lu. Le lease est une date, pas un verrou. Racine de F19.
- **Le worker bypasse les gardes SQL.** Les triggers 008 et 013 s'ouvrent quand `request.jwt.claims` est vide ([013:407-414](../../../supabase/migrations/013_collaboration.sql#L407)) — donc sur connexion `pg` directe. Correct par conception, mais cela signifie que **le worker peut écrire n'importe quel statut sans filet** : c'est le code du worker qui EST la garde.

### 2. Les deux voies d'annulation, dont une seule marche

`cancel_publish_jobs` ([020:246-249](../../../supabase/migrations/020_publish_jobs.sql#L246)) est correcte et conforme règle 15 : elle n'annule que `status in ('scheduled','retrying') and publish_started_at is null`. Elle n'a **qu'un seul appelant applicatif** : `applyStatusIntent` ([content-status.ts:98](../../../apps/web/lib/actions/content-status.ts#L98)). Les autres chemins d'UI qui retirent un contenu du flux — bouton corbeille, archivage en lot, `markTargetPublishedManually` — ne l'appellent pas, et **aucun trigger DB ne rattrape** : les seuls triggers de `content_items` sont `set_updated_at`, `guard_status_transition` (BEFORE UPDATE **OF status** — un `update deleted_at` ne le déclenche pas) et `mark_approval_stale`.

### 3. La couche OAuth : câblée, sans cycle de vie

Le flux est bien en Route Handlers custom (règle 13 ✅), les tokens vont en Vault et ne transitent jamais vers le navigateur (règles 11/12 ✅), la route de *démarrage* exige une session ([route.ts:29](../../../apps/web/app/api/oauth/[provider]/route.ts#L29) appelle `getActiveOrg()`). Ce qui manque est **tout le reste du cycle de vie** : pas d'échange long-lived Meta (`fb_exchange_token` = 0 occurrence en code), `refreshTokens` code en dur `grant_type=refresh_token` pour tous les providers ([index.ts:98-103](../../../apps/web/lib/oauth/index.ts#L98)) et n'a aucun appelant, [tokens/refresh.ts](../../../apps/worker/src/tokens/refresh.ts) n'est qu'un commentaire de flux, aucune déconnexion, aucune comparaison scopes demandés / scopes accordés (le champ `scope` est parsé puis ignoré). **Un compte connecté aujourd'hui est un compte qui meurt en ~2 h, sans alerte.**

### 4. La surface de diagnostic réelle

| Signal attendu | État observé |
|---|---|
| Watchdog jobs en retard (CLAUDE.md §5) | **absent** — zéro `cron.schedule` dans les 21 migrations, pas de répertoire `supabase/functions` |
| Email `publish-failed` (canal GARANTI, §10) | template déclaré, **aucun appelant** ; le worker ne peut de toute façon pas appeler `lib/brevo` (module web) |
| Notification in-app | RPC `emit_notification` ([013:764](../../../supabase/migrations/013_collaboration.sql#L764)) existe, **jamais appelée** par le worker |
| Sentry (web + worker) | **non branché** — `apps/worker/package.json` n'a qu'une dépendance : `pg` |
| Erreurs de lecture Supabase | `error` non déstructuré sur ~52 requêtes de `lib/data` (F14) |
| Erreurs d'écriture des réconciliations | `error` non déstructuré sur 6 requêtes de `content.ts` (F11) |
| Erreurs RPC enqueue/cancel | ignorées volontairement « le watchdog rattrapera » ([content-status.ts:94](../../../apps/web/lib/actions/content-status.ts#L94)) — le watchdog n'existe pas |

**En production, la première personne informée d'un incident sera le client du freelance.**

## Findings (triés par sévérité P0 → P3)

### [P0] F01 — La fenêtre de grâce court-circuite la règle 15 : un post DÉJÀ publié est marqué « échec » → republication manuelle = double post — go-live : bloquant

- **Où** : [apps/worker/src/engine.ts:34](../../../apps/worker/src/engine.ts#L34)
- **Constat** : `processJob` teste la fenêtre de grâce (`now - runAt > 2h` → `store.deadLetter` puis `return`) comme **première instruction**, avant `prepare`, et surtout avant le test `if (job.publishStartedAt)` de la [ligne 61](../../../apps/worker/src/engine.ts#L61) qui porte la règle 15. Un job dont `publish_started_at` est non nul — donc dont la publication est peut-être déjà partie chez le client — est terminalisé **sans qu'aucun `GET /{container}?fields=status_code` ne soit jamais émis**. `deadLetter` ([pg-store.ts:209](../../../apps/worker/src/db/pg-store.ts#L209)) écrit `content_targets.status='failed'`, puis `recomputeParent` ([pg-store.ts:253-259](../../../apps/worker/src/db/pg-store.ts#L253)) bascule `content_items` en `failed`. La garde 008 autorise explicitement `failed → scheduled` ([008:91](../../../supabase/migrations/008_content_status_guard.sql#L91)) : l'admin reprogramme, `enqueue_publish_jobs` crée un job **neuf** (l'ancien est en `dead_letter`, exclu de l'index unique partiel actif [020:115-117](../../../supabase/migrations/020_publish_jobs.sql#L115)), et republie. Le chemin est atteignable parce qu'aucun code n'avance jamais `run_at` : `retryOrFail`, `deferForQuota`, `markAwaitingMedia` ne touchent que `next_attempt_at`, donc `now - runAt` croît sans borne avec la durée d'indisponibilité. Preuve que l'invariant est connu ailleurs mais absent ici : `cancel_publish_jobs` refuse explicitement de toucher un job `publish_started_at` non nul ([020:249](../../../supabase/migrations/020_publish_jobs.sql#L249)).
- **Scénario d'échec / coût à l'échelle** : 09:00, le worker publie un Reel sur l'Instagram d'un client, puis le processus meurt (OOM sur la vidéo, ou l'app worker n'est pas redéployée) juste après le `POST /media_publish` et avant `store.succeed`. Worker à l'arrêt 2 h. 11:05, il repart : `reapExpired` matche `status='publishing'` + lease expiré et repasse le job en `retrying` ([pg-store.ts:87-89](../../../apps/worker/src/db/pg-store.ts#L87)), le claim le reprend car `run_at <= now()`, et `now - runAt = 2h05 > graceWindowMs` → `dead_letter`, aucun appel à Instagram. Ocean affiche « échec de publication » alors que le post est en ligne depuis 09:00. Étienne reprogramme → **2ᵉ post identique sur le compte du client**. Coût : un worker arrêté 2 h envoie en dead_letter d'un coup TOUS les jobs de la fenêtre, y compris ceux déjà publiés.
- **Pourquoi ça bloque le scaling** : la probabilité qu'un incident dépasse 2 h de rattrapage croît avec le nombre de clients, de jobs et de déploiements. Le taux de faux « échec » — donc de republications manuelles — croît linéairement avec le volume, et chaque faux échec est un doublon public chez un client réel.
- **Reco** : réordonner `processJob` en (1) `prepare` (le token est nécessaire pour interroger le conteneur), (2) `if (job.publishStartedAt) return recoverStartedJob(...)` **inconditionnel**, (3) fenêtre de grâce, (4) quota. Poser l'invariant explicitement dans le code : *aucune transition terminale n'est autorisée sur un job à `publish_started_at` non nul tant que le conteneur n'a pas été interrogé*. Ajouter dans `engine.test.ts` un cas « `publishStartedAt` non nul + `runAt` vieux de 3 h ⇒ 0 `deadLetter`, 1 `getContainerStatus`, 1 `succeed` » — [engine.test.ts:186](../../../apps/worker/src/engine.test.ts#L186) ne teste aujourd'hui la fenêtre de grâce qu'avec `publishStartedAt = null`.
- **Effort** : S   **Impact** : fort
- **⚠ Comportement** : oui   **Règle CLAUDE.md** : 15

### [P0] F02 — Ré-éditer un contenu existant DÉTRUIT ses médias (delete sans réinsertion) — go-live : bloquant

- **Où** : [apps/web/lib/actions/content.ts:219](../../../apps/web/lib/actions/content.ts#L219)
- **Constat** : `reconcileMedia` exécute `delete from content_media where org_id=… and content_item_id=…` **puis** `if (!media.length) return` ([content.ts:219-220](../../../apps/web/lib/actions/content.ts#L219)) — le delete est inconditionnel et son erreur n'est pas lue. Or le payload n'admet que des médias porteurs d'un `libraryAssetId` uuid obligatoire ([content.ts:29](../../../apps/web/lib/actions/content.ts#L29)), et `draftFromContent` reconstruit les médias d'un contenu existant **sans ce champ** ([composer-types.ts:151-164](../../../apps/web/components/app/studio/composer/composer-types.ts#L151) : il mappe `id/type/thumbUrl/width/height/durationSec/fileSizeMb/mimeType/altText`, jamais `libraryAssetId` ni `crop`). `mediaFromLibrary` ([composer-types.ts:86](../../../apps/web/components/app/studio/composer/composer-types.ts#L86)) est le SEUL endroit du dépôt qui pose ce champ. `handleSave` filtre donc tout (`m.libraryAssetId ? [...] : []`, [composer-screen.tsx:144-148](../../../apps/web/components/app/studio/composer/composer-screen.tsx#L144)) et envoie `media: []`. Le `id` exposé par le loader EST pourtant l'id de l'asset ([content-media.ts:118](../../../apps/web/lib/data/content-media.ts#L118)) : le champ manque juste au mapping. Rien ne bloque côté DB — la policy `content_media_delete` autorise tout membre d'org et le trigger de cardinalité est `after insert or update` seulement ([012:263-265](../../../supabase/migrations/012_media.sql#L263)).
- **Scénario d'échec / coût à l'échelle** : Étienne ouvre un brouillon client déjà composé (3 slides), corrige une faute dans la légende, clique Enregistrer. L'action renvoie `ok:true`, un toast « n médias ignorés » s'affiche **puis** un toast de succès, et les 3 lignes `content_media` viennent d'être supprimées. Reproductible à 100 % sur tout contenu en `idea`/`draft`/`changes_requested` (les statuts de `RECONCILABLE_STATUSES`, [content.ts:71](../../../apps/web/lib/actions/content.ts#L71)). Aggravant : la FK `annotation_content_media_id … on delete cascade` ([013:138-139](../../../supabase/migrations/013_collaboration.sql#L138)) fait disparaître au passage les annotations du client (voir F24).
- **Pourquoi ça bloque le scaling** : le jour où l'upload TUS sera câblé, ce chemin subsiste — toute ré-édition d'un contenu dont les médias ne viennent pas d'être re-piochés dans la médiathèque videra la liaison. Plus il y a de contenus par client, plus la perte est massive, silencieuse et non auditable.
- **Reco** : (1) ajouter `libraryAssetId: m.id` et `crop` dans le mapping de `draftFromContent` ; (2) surtout, rendre `reconcileMedia` non destructif — diff/upsert sur `(content_item_id, media_asset_id, position)` plutôt qu'un `delete`-all, et ne jamais supprimer sur payload vide. Un `delete` inconditionnel suivi d'un `return` anticipé est un patron à bannir dans une réconciliation.
- **Effort** : S   **Impact** : fort
- **⚠ Comportement** : oui   **Règle CLAUDE.md** : aucune (contrat action ↔ composer ; adjacent r27)

### [P0] F03 — Mettre un contenu programmé à la corbeille ne désarme pas la file : il est publié quand même — go-live : bloquant

- **Où** : [apps/web/lib/actions/content.ts:363](../../../apps/web/lib/actions/content.ts#L363)
- **Constat** : `trashContent` pose `deleted_at` et **rien d'autre** ([content.ts:355-372](../../../apps/web/lib/actions/content.ts#L355)) : ni changement de statut, ni `cancel_publish_jobs`. Aucun trigger DB ne rattrape (la garde 008 est `before update OF status`, un update de `deleted_at` seul ne la déclenche pas). Côté worker, le claim ne joint jamais `content_items` ([pg-store.ts:55-71](../../../apps/worker/src/db/pg-store.ts#L55)) et `processJob` ne relit ni le statut parent ni `deleted_at` — sa seule garde est la fenêtre de grâce, qui ne se déclenche pas pour un job claimé à l'heure. Le bouton est offert sur un contenu `scheduled` : `READ_ONLY` ne couvre que `publishing/published/partially_published` ([content-actions.tsx:17](../../../apps/web/components/app/studio/content-actions.tsx#L17)) — et le bouton destructif rendu pour `scheduled` s'intitule littéralement « annuler la programmation » ([content-actions.tsx:100-103](../../../apps/web/components/app/studio/content-actions.tsx#L100)) alors qu'il ne fait qu'un soft-delete. Même trou pour `scheduleContentItem({scheduledAt: null})` ([content.ts:301-311](../../../apps/web/lib/actions/content.ts#L301)) : l'update passe, `enqueue_publish_jobs` retourne 0 car `v_at is null` ([020:177-180](../../../supabase/migrations/020_publish_jobs.sql#L177)), et le job garde son ancien `run_at`.
- **Scénario d'échec / coût à l'échelle** : le client dit « finalement on ne publie pas ce post ». Étienne le met à la corbeille. Le post disparaît de l'app (le loader filtre `deleted_at`). Le lendemain à 10:00, le worker claime le job resté `scheduled` et publie sur le compte Instagram **réel** du client un contenu que tout le monde croit supprimé. Si le contenu est ensuite purgé (`hardDeleteContent`), le job disparaît par cascade FK ([020:88-89](../../../supabase/migrations/020_publish_jobs.sql#L88)) en plein vol et le post reste en ligne sans aucune trace en base.
- **Pourquoi ça bloque le scaling** : chaque contenu annulé tardivement devient une bombe à retardement. À 20 clients et 100 posts/mois, l'incident finit statistiquement par arriver — et c'est exactement la « publication non voulue chez un client » que CLAUDE.md §12 qualifie de destructrice pour la confiance produit.
- **Reco** : dans `trashContent`, appeler `cancel_publish_jobs` **avant** de poser `deleted_at`, et refuser (ou forcer un passage par `cancel`) si un job a `publish_started_at` non nul. Idem dans `scheduleContentItem` quand `scheduledAt === null`. Renommer/dissocier le bouton « annuler la programmation » de la corbeille. Ceinture et bretelles côté worker : ajouter au claim `and exists (select 1 from content_items ci where ci.id = pj.content_item_id and ci.deleted_at is null and ci.status in ('scheduled','publishing','approved','partially_published'))` — la file ne doit jamais être la seule source de vérité de « faut-il publier ».
- **Effort** : S   **Impact** : fort
- **⚠ Comportement** : oui   **Règle CLAUDE.md** : 15, 18

### [P0] F04 — Une connexion Meta rattache TOUTES les Pages/comptes IG du compte Facebook au client cible — go-live : bloquant

- **Où** : [apps/web/lib/oauth/tokens.ts:179](../../../apps/web/lib/oauth/tokens.ts#L179)
- **Constat** : `persistPlatformConnection` boucle sur `resolved.subAccounts` **sans aucun filtre** et écrit un `social_accounts` par sous-compte avec `client_id: ctx.clientId` ([tokens.ts:178-181](../../../apps/web/lib/oauth/tokens.ts#L178)). `resolveMeta` ([identity.ts:74-98](../../../apps/web/lib/oauth/identity.ts#L74)) énumère TOUTES les Pages retournées par `/me/accounts` et pousse, pour chacune, la Page **et** son `instagram_business_account`. Le menu propose « Instagram / Facebook / TikTok » mais **jette le choix de plateforme** : seul `provider` part dans l'URL ([connect-account-menu.tsx:38](../../../apps/web/components/app/settings/connect-account-menu.tsx#L38)), et le state signé ne porte aucune plateforme. Il n'existe aucun écran de sélection des comptes à rattacher, ni aucun chemin de suppression (`grep .delete() social_accounts` = 0 hit ; le « disconnect » de l'onboarding n'est qu'un toast).
- **Scénario d'échec / coût à l'échelle** : Étienne administre les Pages de ses 6 clients depuis un seul Business Manager. Il ouvre les réglages du client « Boulangerie Martin », clique « Connecter Instagram » : les 6 Pages Facebook **et** les 6 comptes IG de tous ses clients sont créés en `social_accounts` avec `client_id = Boulangerie Martin`. Aggravant : `emptyDraft` **présélectionne** le premier compte instagram trouvé ([composer-types.ts:104-116](../../../apps/web/components/app/studio/composer/composer-types.ts#L104)) et `getSocialAccounts` trie par `created_at asc` — donc la cible par défaut de chaque nouveau post est le premier compte IG renvoyé par Meta, potentiellement celui d'un autre client. `reconcileTargets` ne revalide que sur `org_id + client_id` : tout est dans la même org, **aucune RLS ne peut l'attraper**. Second effet : `getClient` fait un `.maybeSingle()` sur `social_accounts` filtré `client_id + platform=instagram` ([clients.ts:98-104](../../../apps/web/lib/data/clients.ts#L98)) → erreur sur plusieurs lignes, le nombre d'abonnés retombe à 0.
- **Pourquoi ça bloque le scaling** : croît linéairement avec le nombre de clients par freelance, puis explose à l'ouverture SaaS (une agence à 40 Pages crée 80 lignes `social_accounts` **par client et par connexion**). Le nettoyage est manuel et le même compte IG physique existe en N lignes que l'index unique `(content_item_id, social_account_id)` ne peut pas dédupliquer.
- **Reco** : découper le callback en deux temps — (1) persister `platform_connections` + son secret, puis rediriger vers un écran « choisir les comptes à rattacher à *client* » listant `resolved.subAccounts` ; (2) une Server Action Zod-validée crée les `social_accounts` sélectionnés. Transition immédiate et peu coûteuse : passer `platform` dans le state depuis `connect-account-menu`, filtrer `subAccounts` dessus, et n'auto-rattacher que si `subAccounts.length === 1`. Prévoir dès maintenant un chemin de déconnexion.
- **Effort** : M   **Impact** : fort
- **⚠ Comportement** : oui   **Règle CLAUDE.md** : aucune (règles 1/3 respectées — fuite métier intra-org, pas RLS)

### [P0] F05 — Cycle de vie du token Meta absent : pas d'échange long-lived, et le refresh utilise un grant_type que Meta n'accepte pas — go-live : bloquant

- **Où** : [apps/web/lib/oauth/index.ts:93](../../../apps/web/lib/oauth/index.ts#L93)
- **Constat** : `exchangeCode` ([index.ts:62-87](../../../apps/web/lib/oauth/index.ts#L62)) ne fait qu'un `grant_type=authorization_code` et **rend le token tel quel** : côté Facebook Login serveur c'est un token utilisateur COURT (~1-2 h). `resolveIdentity` est appelé immédiatement après ([callback/route.ts:49](../../../apps/web/app/api/oauth/[provider]/callback/route.ts#L49)) et récupère les `page.access_token` ([identity.ts:76-95](../../../apps/web/lib/oauth/identity.ts#L76)) — dérivés d'un token court, ils sont eux aussi courts, et c'est **ce** token qui est chiffré dans `social_account_secrets`. Aucun appel `fb_exchange_token` nulle part (grep repo entier : 0 occurrence en code). Et `refreshTokens` ([index.ts:98-103](../../../apps/web/lib/oauth/index.ts#L98)) envoie `grant_type=refresh_token` + `refresh_token` pour **tous** les providers, alors que Meta n'émet aucun refresh_token et exige `grant_type=fb_exchange_token&fb_exchange_token=<token>`. `tokens.ts:170` écrit donc un `token_expires_at` d'environ +1-2 h que personne ne relit. [docs/PRD.md:489](../../../docs/PRD.md#L489) acte pourtant « le user token racine (60 j) est porté par platform_connections ».
- **Scénario d'échec / coût à l'échelle** : Étienne connecte Instagram lundi 14:00, programme un post pour mardi 09:00.
