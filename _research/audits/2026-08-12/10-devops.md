# Audit — DevOps, déploiement et exploitation (DATE-MANQUANTE)

## Verdict

La dimension DevOps d'Ocean est **la moins mûre du dépôt, et c'est aujourd'hui elle qui empêche un usage réel**. Trois constats structurent le reste : (1) **la CI n'a jamais tourné une seule fois** — 7 runs depuis le 21/07, 7 échecs, le job `db` meurt sur une collision de version de migration (`012` en double) et le job `web` meurt sur une incompatibilité Node 20 / pnpm 11.1.2, donc ni les leak tests pgTAP (règle 8), ni Biome, ni le typecheck, ni le build n'ont jamais été exécutés en CI ; (2) **le worker — le seul composant qui écrit chez un tiers — n'a aucun artefact de déploiement, aucun job de CI, aucun log métier, aucun healthcheck, et démarre en `STUB_MODE = true` en dur** : déployé tel quel sur la base de production comme le prescrit le runbook, il marque des contenus « publié » avec des permalinks `https://stub.local/...` sans rien publier ; (3) **l'observabilité est à zéro** : pas de Sentry, pas de PostHog, `/api/health` est une constante, aucun watchdog `pg_cron`, aucun log applicatif côté web — un worker mort est strictement indétectable jusqu'à la réclamation d'un client. Pour un **usage réel immédiat**, cela signifie qu'aucune publication ne peut être considérée comme fiable tant que le worker n'a pas (a) une image reproductible, (b) un mode live/stub piloté par l'environnement, (c) un canal d'alerte indépendant de lui-même. **Risque à 5 ans** : le déploiement repose entièrement sur la mémoire d'une personne — deux canaux manuels non ordonnés (SQL collé dans le SQL Editor d'un côté, webhook Coolify de l'autre), aucun staging, aucun rollback, aucune trace de ce qui est réellement appliqué en base, et une configuration d'infrastructure qui n'existe que dans l'UI Coolify. Chaque migration élargit l'écart entre le dépôt et la production, et le jour où il faut reconstruire (nouveau VPS, restauration, second contributeur), rien ne garantit que la base soit reproductible.

## Fonctionnement réel observé

### 1. Deux chaînes de déploiement indépendantes, toutes deux manuelles

Le schéma et le code partent par des canaux séparés, sans ordre imposé ni vérification croisée :

- **Schéma** → Étienne copie-colle les fichiers `deploy/*.sql` dans le SQL Editor du projet `hgdeopkmkwyoumsfggrm` ([GO-LIVE-points-1-2.md:8](../../../deploy/GO-LIVE-points-1-2.md#L8)). La CI n'exécute jamais `supabase db push` ni `link` — c'est explicite ([ci.yml:29](../../../.github/workflows/ci.yml#L29)) — et aucun `deploy/*.sql` n'écrit dans `supabase_migrations.schema_migrations` : **il n'existe aucun ledger de ce qui est réellement appliqué en ligne**, seulement un markdown.
- **Code** → `git push` sur `main` puis appel manuel d'un webhook Coolify `GET /api/v1/deploy?uuid=…` ([GO-LIVE-points-1-2.md:33-35](../../../deploy/GO-LIVE-points-1-2.md#L33)), totalement découplé de l'état de la CI.

### 2. Une seule app Coolify, une seule image, web uniquement

Le seul `Dockerfile` du dépôt construit exclusivement l'app web : le stage `deps` ne copie que `apps/web/package.json` ([Dockerfile:11](../../../Dockerfile#L11)), le build est `pnpm --filter web build` ([Dockerfile:20](../../../Dockerfile#L20)), l'entrypoint est `node apps/web/server.js` ([Dockerfile:38](../../../Dockerfile#L38)). L'image est par ailleurs propre : multi-stage, `node:22-alpine`, sortie `standalone` ([next.config.ts:9](../../../apps/web/next.config.ts#L9)), utilisateur non-root. Il n'y a **ni `HEALTHCHECK`, ni `ARG` pour les `NEXT_PUBLIC_*`**, et **aucun artefact pour le worker** : le runbook prévoit une 2e app Coolify en buildpack avec `pnpm install` + `pnpm --filter worker start`, c'est-à-dire `tsx src/index.ts` ([apps/worker/package.json:7](../../../apps/worker/package.json#L7)) — `tsx` étant en `devDependencies` (ligne 18) et le worker n'ayant **aucun script `build`**.

### 3. La CI : deux jobs, zéro run vert

`.github/workflows/ci.yml` est le seul workflow. Il contient `db` ([ci.yml:15](../../../.github/workflows/ci.yml#L15)) et `web` ([ci.yml:107](../../../.github/workflows/ci.yml#L107)), **aucun job worker**, aucun job de déploiement, aucun `docker build`. Vérifié par exécution réelle (`gh run list` / `gh run view 29933865010`) :

- `db` s'arrête au step `supabase start` sur `duplicate key value violates unique constraint "schema_migrations_pkey" … Key (version)=(012) already exists` → `db reset`, `supabase test db`, le gate advisors, l'assertion `*_secrets` et le check anti-patterns sont **tous skippés**.
- `web` s'arrête au step `setup-node` : `This version of pnpm requires at least Node.js v22.13` puis `ERR_UNKNOWN_BUILTIN_MODULE: node:sqlite` → `pnpm install`, Biome, typecheck et build sont **tous skippés**.
- Et même s'ils démarraient : Biome ([ci.yml:130](../../../.github/workflows/ci.yml#L130)) et Typecheck ([ci.yml:134](../../../.github/workflows/ci.yml#L134)) sont en `continue-on-error: true`. Le seul gate réel serait `pnpm build`, qui ne construit que `web`.

### 4. Le worker en exploitation

Boucle `tick` de 5 s : `reapExpired()` puis jusqu'à 10 `claim()` ([index.ts:52-66](../../../apps/worker/src/index.ts#L52)). La machine à états est correcte et l'invariant règle 15 est réellement tenu (`publish_started_at` posé avant le publish, [pg-store.ts:116](../../../apps/worker/src/db/pg-store.ts#L116)), avec 7 tests unitaires qui le prouvent — **que rien n'exécute**. Côté exploitation en revanche : aucun serveur HTTP (grep `createServer|listen(` sur `apps/worker/src` = 0), aucun heartbeat en base, la boucle attrape toutes les erreurs de tick et continue indéfiniment ([index.ts:99-103](../../../apps/worker/src/index.ts#L99)) — un worker qui échoue à 100 % reste « vivant » pour Coolify. Le seul `process.exit(1)` ([index.ts:113](../../../apps/worker/src/index.ts#L113)) n'est atteignable que si `main()` rejette, jamais sur une panne DB persistante.

### 5. Observabilité : néant

Aucune dépendance `@sentry/*` ni `posthog-*` dans les trois `package.json`, aucun `apps/web/instrumentation.ts`, aucun `onRequestError`. `grep 'console\.'` sur `apps/web` (app, lib, components, hooks, proxy.ts) = **0 occurrence** : le conteneur web ne produit aucun log applicatif. `/api/health` est une constante de 5 lignes ([route.ts:3](../../../apps/web/app/api/health/route.ts#L3)). `supabase/functions/` n'existe pas, aucun `cron.schedule` dans les 22 migrations ni dans `deploy/` : le watchdog `pg_cron` décrit en CLAUDE.md §5 — **le seul filet indépendant du worker** — n'a jamais été construit, seule la valeur d'enum `watchdog_alert` existe ([002_enums.sql:106](../../../supabase/migrations/002_enums.sql#L106)).

## Findings (triés par sévérité P0 → P3)

### [P0] Collision de version `012` : le job `db` de la CI n'a jamais tourné — go-live : bloquant

- **Où** : [supabase/migrations/012_media_storage.sql:1](../../../supabase/migrations/012_media_storage.sql#L1) (collision avec `012_media.sql`) — déclenché par [ci.yml:30](../../../.github/workflows/ci.yml#L30)
- **Constat** : deux fichiers partagent le préfixe `012`. Le CLI Supabase dérive la version des chiffres de tête et l'insère en clé primaire dans `supabase_migrations.schema_migrations`. Log réel du run 29933865010 : `Applying migration 012_media_storage.sql...` → `ERROR: duplicate key value violates unique constraint "schema_migrations_pkey" (SQLSTATE 23505) / Key (version)=(012) already exists`. Le job meurt au step `supabase start`, donc `db reset`, `supabase test db`, le gate advisors, l'assertion `*_secrets deny-all` et le check anti-patterns **n'ont jamais été exécutés une seule fois** (7 runs depuis le 21/07, 7 en échec, aucun run vert dans l'histoire du dépôt). `cut -c1-3 | sort | uniq -d` sur `supabase/migrations/` ne remonte que `012` : c'est la seule collision.
- **Scénario d'échec / coût à l'échelle** : ce n'est pas théorique, c'est déjà arrivé. La faille corrigée par la migration 021 (anon pouvait appeler `store_integration_secret` et écrire dans le Vault) **était couverte par un test committé avant le fix** ([019_integration_secrets.test.sql:40](../../../supabase/tests/019_integration_secrets.test.sql#L40), `not has_function_privilege('authenticated', …)`). Ce test n'a jamais tourné ; la faille est partie en production et a été trouvée à la main via `get_advisors`. Le même scénario se rejouera sur n'importe quelle régression RLS : un leak test écrit, committé, jamais exécuté, donne une fausse assurance totale. Effet secondaire immédiat : `supabase db reset` et `db push` sont cassés pour **tout rejeu depuis zéro** — staging, restauration après incident, arrivée d'un second contributeur.
- **Pourquoi ça bloque le scaling** : chaque migration ajoutée alourdit un filet qui ne se déclenche pas. La règle 8 (leak test pgTAP par table) et la checklist « Avant deploy » de CLAUDE.md §7 reposent entièrement sur ce job.
- **Reco** : renommer `012_media_storage.sql` en `022_media_storage.sql` (le runner local saute les `*_storage.sql` par suffixe, [run-pgtap.sh:22-28](../../../scripts/run-pgtap.sh#L22) — le renommage préserve ce comportement), relancer la CI et **exiger un run vert avant tout nouveau déploiement**. Ajouter un step qui échoue si deux fichiers de `supabase/migrations/` partagent les 3 premiers caractères.
- **Effort** : S   **Impact** : fort
- **⚠ Comportement** : non   **Règle CLAUDE.md** : 8

### [P0] `STUB_MODE` est une constante en dur : un worker déployé écrit de faux permalinks et marque le contenu « publié » — go-live : bloquant

- **Où** : [apps/worker/src/publishers/index.ts:21](../../../apps/worker/src/publishers/index.ts#L21)
- **Constat** : `export const STUB_MODE = true` est une constante littérale, sans lecture d'environnement ni garde de démarrage. Elle est propagée à `createContextProvider`/`createQuotaChecker` ([index.ts:76-77](../../../apps/worker/src/index.ts#L76)) : token absent → contexte factice `{ accessToken: 'stub-no-token' }`, quota toujours OK. Le stub renvoie un succès déterministe avec `externalPostId: 'stub-instagram-post-…'` et `permalink: 'https://stub.local/…'` ([publishers/stub.ts:22-24](../../../apps/worker/src/publishers/stub.ts#L22)), que `succeed()` écrit **tel quel** dans `content_targets.permalink` puis agrège en `content_items.status = 'published'` ([pg-store.ts:146-163](../../../apps/worker/src/db/pg-store.ts#L146) + `recomputeParent`). Le permalink est rendu en lien cliquable dans l'UI ([content-targets.tsx:122](../../../apps/web/components/app/studio/content-targets.tsx#L122)). Le mode stub est une décision actée ; **ce qui manque, c'est le garde-fou de déploiement** — `env.ts` ne contrôle que le port 6543, rien n'empêche un worker stub de pointer la base de production.
- **Scénario d'échec / coût à l'échelle** : l'étape 4 du runbook prescrit explicitement de créer l'app worker Coolify sur le `DATABASE_URL` de production, en rassurant à tort l'opérateur (« Le worker démarre en STUB … sans publier chez un client », [GO-LIVE-points-1-2.md:50-70](../../../deploy/GO-LIVE-points-1-2.md#L50)). Étienne programme un post pour un vrai client : 5 secondes plus tard l'app affiche « Publié » avec un lien `https://stub.local/...`. Rien n'a été publié sur Instagram, et le client voit sur le portail un contenu marqué publié qui n'existe pas — « donnée inventée affichée au client », en pire puisque `enqueue_publish_jobs` filtre `ct.status not in ('published','canceled','skipped')` ([020_publish_jobs.sql:195](../../../supabase/migrations/020_publish_jobs.sql#L195)) : la cible n'est plus ré-enfilable depuis l'app, seul du SQL manuel la débloque.
- **Pourquoi ça bloque le scaling** : une constante de compilation n'est pas observable à l'exploitation — rien dans les logs ni dans l'UI ne dit que le worker en production est un simulateur. Le jour où les creds Meta arrivent, rien ne garantit que l'instance déployée a changé de mode.
- **Reco** : lire le mode depuis l'environnement (`WORKER_PUBLISH_MODE=stub|live`) et **refuser le démarrage en mode stub si `DATABASE_URL` pointe la base de production** (même logique que le refus du port 6543, [env.ts:36](../../../apps/worker/src/env.ts#L36)). En mode stub, écrire `content_targets.status = 'skipped'` avec un `last_error` explicite plutôt que `'published'`, et **ne jamais poser de permalink**. Exposer le mode dans le log de démarrage (déjà fait) ET dans le futur `/health` du worker.
- **Effort** : S   **Impact** : fort
- **⚠ Comportement** : oui   **Règle CLAUDE.md** : aucune (mais casse l'invariant produit « ce qui est affiché publié l'est »)

### [P1] Le worker n'a ni image ni build : son runtime de production est `tsx`, une devDependency — go-live : bloquant

- **Où** : [apps/worker/package.json:7](../../../apps/worker/package.json#L7) et :18 ; [Dockerfile:11](../../../Dockerfile#L11)
- **Constat** : le seul `Dockerfile` du dépôt ne copie que `apps/web/package.json` et ne construit que `web` — le worker n'entre jamais dans une image. `apps/worker` n'a **aucun script `build`**, son `tsconfig` est en `noEmit: true`, et `start` vaut `tsx src/index.ts` avec `tsx` en `devDependencies`. Il n'existe ni `Dockerfile.worker`, ni `nixpacks.toml`, ni `Procfile`, ni compose (`git ls-files` sur ces motifs → uniquement `/Dockerfile` et `/.dockerignore`). La configuration réelle de la 2e app Coolify n'existe qu'en prose ([GO-LIVE-points-1-2.md:52-53](../../../deploy/GO-LIVE-points-1-2.md#L52) : Install `pnpm install`, Start `pnpm --filter worker start`) et `.planning/SESSION.md:127` confirme « Pas d'app worker ».
- **Scénario d'échec / coût à l'échelle** : deux modes, tous deux silencieux jusqu'au boot. (a) Si le buildpack pose `NODE_ENV=production` (comportement courant), `pnpm install` élague les devDependencies, `tsx` est absent et le conteneur part en crash-loop — visible dans Coolify, mais indistinguable d'un worker sans jobs pour qui ne regarde pas. (b) Si l'opérateur choisit le build pack « Dockerfile » — le seul évident puisqu'un Dockerfile est à la racine — le stage `deps` casse dès `pnpm install --frozen-lockfile` (le lockfile déclare 3 importers, un seul est copié). Dans les deux cas, aucun `publish_job` n'est claimé et **rien n'alerte** (le watchdog n'existe pas, cf. finding suivant).
- **Pourquoi ça bloque le scaling** : sans artefact figé, chaque redeploy rejoue une résolution de dépendances différente de celle testée, et il est impossible de faire tourner deux versions côte à côte pendant un rollout. La configuration (start command, env, replicas, grace period) n'existe que dans l'UI Coolify : non versionnée, perdue à la recréation du VPS.
- **Reco** : créer `apps/worker/Dockerfile` multi-stage (deps → `tsc` vers `dist/` → runner `node:22-alpine` non-root, `CMD ["node","dist/index.js"]`), sortir `tsx` du chemin d'exécution production, et renommer le Dockerfile racine en `apps/web/Dockerfile` pour lever l'ambiguïté. Versionner `docs/deploy/coolify.md` : les 2 apps, leur build pack, leurs env, la **grace period ≥ 150 s** (lease de 2 min) et la consigne « replicas = 1 » tant que le rate limiting par `social_account` n'est pas partagé entre process (règle 19).
- **Effort** : L   **Impact** : fort
- **⚠ Comportement** : oui   **Règle CLAUDE.md** : 17, 18, 19

### [P1] Aucun média réel ne s'affichera : le host Supabase Storage n'est pas autorisé pour `next/image` — go-live : bloquant

- **Où** : [apps/web/next.config.ts:14](../../../apps/web/next.config.ts#L14)
- **Constat** : `images.remotePatterns` n'autorise que `images.pexels.com`, et il n'y a ni `unoptimized` ni loader custom. Or les URLs réellement produites viennent de `getPublicUrl()` et `createSignedUrls()` ([content-media.ts:43 et 50](../../../apps/web/lib/data/content-media.ts#L43), [pro.ts:268 et 275](../../../apps/web/lib/data/pro.ts#L268)), donc du host `<ref>.supabase.co`, et sont passées directement à `next/image` ([media-thumb.tsx:36](../../../apps/web/components/shared/media-thumb.tsx#L36) + 16 autres composants grid / studio / library / portal).
- **Scénario d'échec / coût à l'échelle** : dès que l'upload TUS livrera le premier média réel, chaque vignette part sur `/_next/image?url=https://<ref>.supabase.co/storage/...` et l'optimiseur répond 400 « hostname is not configured under images ». Le `onError` bascule sur l'icône de repli ([media-thumb.tsx:43](../../../apps/web/components/shared/media-thumb.tsx#L43)) : grille de preview IG, studio, bibliothèque et **portail client** entièrement gris — y compris devant un vrai client en validation. Le symptôme fera penser à un problème de policy Storage/RLS et se cherchera au mauvais endroit pendant des heures.
- **Pourquoi ça bloque le scaling** : chaque nouveau bucket ou CDN retombera dans le même piège, et la correction naïve (`**.supabase.co`) transformerait `/_next/image` en proxy d'optimisation ouvert vers n'importe quel projet Supabase.
- **Reco** : ajouter un remotePattern strict `{ protocol:'https', hostname: <host dérivé de NEXT_PUBLIC_SUPABASE_URL>, pathname:'/storage/v1/object/**' }` — calculé au chargement de la config, jamais en dur, pour rester valable en staging. Fixer `minimumCacheTTL` **en dessous** du TTL des URLs signées pour ne pas servir une image dont l'URL source a expiré. Retirer `pexels` une fois les données de démo parties.
- **Effort** : S   **Impact** : fort
- **⚠ Comportement** : oui   **Règle CLAUDE.md** : 20

### [P1] Un job qui épuise ses tentatives reste figé en `claimed` à vie, sans recours depuis l'UI — go-live : dégradé

- **Où** : [apps/worker/src/db/pg-store.ts:89](../../../apps/worker/src/db/pg-store.ts#L89) (reaper borné par `attempts < max_attempts`) + [pg-store.ts:62](../../../apps/worker/src/db/pg-store.ts#L62) (claim n'inclut ni `claimed` ni `publishing`)
- **Constat** : le reaper ne recycle un lease expiré que si `attempts < max_attempts`. Au-delà, le job reste `claimed`/`publishing` pour toujours : plus aucun worker ne le reprend. Le commentaire ligne 81 délègue explicitement ce cas « au watchdog pg_cron (indépendant, §5) qui notifie » — composant qui n'existe pas. Aucun `failed_at`, aucun `last_error`, aucune notification n'est écrite : **le job meurt muet**. `retryOrFail` plafonne `attempts` à `max_attempts - 1` ([pg-store.ts:168](../../../apps/worker/src/db/pg-store.ts#L168)) : seul le reaper peut porter le compteur au maximum, donc l'état zombie exige deux expirations de lease successives (crash worker pendant un traitement, deux fois) — composé, mais atteignable.
- **Scénario d'échec / coût à l'échelle** : `content_items.status` reste sur `'publishing'` (posé par `markPublishStarted`), l'UI affiche « publication en cours » indéfiniment. Étienne reprogramme depuis le studio : `enqueue_publish_jobs` fait `on conflict do update set run_at` **sans réinitialiser le statut** ([020_publish_jobs.sql:196-198](../../../supabase/migrations/020_publish_jobs.sql#L196)) → l'action retourne un succès et rien ne part. `cancel_publish_jobs` ne cible que `scheduled`/`retrying` ([020:245-249](../../../supabase/migrations/020_publish_jobs.sql#L245)) → impossible d'annuler non plus. **Seul du SQL service_role débloque la cible.**
- **Pourquoi ça bloque le scaling** : chaque incident laisse un déchet permanent dans la file. À 20 clients, un incident plateforme (Meta down 15 min) génère une vague de cibles définitivement non republiables, les KPI de publication deviennent faux, et la seule détection est une requête SQL manuelle.
- **Reco** : dans `reapExpired`, traiter les deux cas — `attempts < max_attempts` → `retrying` (actuel) ; `attempts >= max_attempts` → réutiliser `failPermanent` : `status='failed'`, `failed_at=now()`, `last_error='lease_expired_max_attempts'`, passage de `content_targets` en `failed` + `recomputeParent`, plus un `log.error` par job ainsi achevé. Ajouter un test dans `engine.test.ts` couvrant lease expiré + `attempts = max`.
- **Effort** : S   **Impact** : fort
- **⚠ Comportement** : oui   **Règle CLAUDE.md** : 18

### [P1] Le watchdog `pg_cron` n'existe pas : un worker mort ne déclenche aucune alerte — go-live : dégradé

- **Où** : `supabase/migrations/` (aucun `cron.schedule` / `pg_cron` / `pg_net` sur les 22 migrations ni les 16 fichiers `deploy/`) ; répertoire `supabase/functions/` absent ; [002_enums.sql:106](../../../supabase/migrations/002_enums.sql#L106) (seule trace : la valeur d'enum `watchdog_alert`)
- **Constat** : CLAUDE.md §5 impose un « watchdog pg_cron indépendant (1×/5 min) : jobs en retard > 2 min non claimés → Edge Function → email Brevo ». Rien n'existe : `create extension` ne déclare que `pgcrypto` ([001:1](../../../supabase/migrations/001_extensions_schema_utils.sql#L1)), aucun job cron n'est planifié, et les deux Edge Functions prévues (`media-cleanup`, `watchdog-notify`) n'ont même pas de répertoire. Le template Brevo `watchdog-alert` est déclaré côté type ([transactional.ts:23](../../../apps/web/lib/brevo/transactional.ts#L23)) sans aucun appelant. **Conséquence structurelle : la seule chose qui sait qu'un job aurait dû partir, c'est le worker lui-même — s'il est mort, personne ne le sait.**
- **Scénario d'échec / coût à l'échelle** : redeploy un vendredi soir, `DATABASE_URL` écrasée ou mot de passe DB tourné. Le worker boucle sur `tick failed` ([index.ts:102](../../../apps/worker/src/index.ts#L102)) mais le process reste vivant, donc Coolify affiche l'app en vert. Les 12 posts programmés du week-end restent `scheduled`, `run_at` dépassé. Aucun email, aucune notification in-app, aucun Sentry. Découvert lundi par les clients — bien au-delà de la fenêtre de grâce de 2 h, donc tous en `dead_letter`.
- **Pourquoi ça bloque le scaling** : avec 1 client c'est un incident ; avec 20 clients et 200 posts/semaine, une panne de quelques heures non détectée détruit la confiance produit d'un coup, et il n'existe aucune trace pour reconstituer ce qui n'est pas parti.
- **Reco** : migration 022 : `create extension pg_cron` + `pg_net`, job toutes les 5 min comptant les `publish_jobs` en `('scheduled','retrying')` avec `run_at < now() - interval '2 minutes'` **ainsi que** les jobs figés en `claimed` avec lease expiré (finding précédent) ; si `count > 0`, `net.http_post` vers une Edge Function `watchdog-notify` qui envoie `watchdog-alert` à Étienne, avec dédoublonnage par fenêtre de 30 min. Le sink existe déjà (enum de notification + icône UI), seul le producteur manque. **Le watchdog doit être indépendant du worker — c'est tout son intérêt.**
- **Effort** : M   **Impact** : fort
- **⚠ Comportement** : oui   **Règle CLAUDE.md** : aucune (CLAUDE.md §5 « filets de sécurité »)

### [P1] Le worker n'expose ni port HTTP ni heartbeat : Coolify ne peut pas détecter un worker figé — go-live : dégradé

- **Où** : [apps/worker/src/index.ts:98-105](../../../apps/worker/src/index.ts#L98) ; `apps/worker/src/` (grep `createServer|listen(|express|fastify` → 0 match)
- **Constat** : le worker est un process pur, sans serveur HTTP : Coolify ne dispose d'aucun healthcheck et se contente de constater que le process vit. Or la boucle attrape **toutes** les erreurs de tick et continue indéfiniment, sans compteur d'échecs consécutifs : un worker qui échoue sur 100 % de ses ticks reste « en vie ».
